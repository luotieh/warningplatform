# 流量分析全量证据摘要与模型输入改造任务书

## 1. 任务目标

将当前“按位置取首/中/末明细”的模型输入方式改为：后端扫描全部命中记录，预先计算确定性统计量、历史趋势、协议解析和关联特征；对重复流量压缩，对重要/可疑/未知证据保留样本；统计量用于替代机械计数，把上下文预算留给大模型进行跨报文、跨会话、时序和语义关系分析，发现人工难以直接识别的攻击链、隐蔽关联和异常组合，并据此完成安全研判和报告表达。

改造不得改变事件列表、事件详情、命中明细弹窗、归档、审核和 PCAP 下载的现有行为。数据库中的原始明细必须继续完整保存。

## 2. 明确范围

### 本次改造的唯一业务目标

本次改造聚焦于**生成报告时发送给大模型的上下文构造**：在报告生成请求前，全量分析该事件的命中明细、历史记录和已有处置，形成高质量、可追溯、可解释的模型输入；模型据此生成安全事件报告。事件采集、聚合入库、事件列表展示、命中明细展示和 PCAP 下载不是本次改造目标，除非为生成上下文增加只读查询或派生字段。

本次报告生成链路必须同时支持：

- 后端确定性统计，避免模型浪费 token 做简单计数；
- 大模型对跨报文、跨会话、时序和语义关系的深层推理；
- 报告给出“危险攻击概率”（0–100%）、概率依据、关键证据和不确定性；
- 报告明确区分确定性事实、模型推理和待验证假设。

### 后端

修改范围限定为 `vulnscan-backend/traffic/**`：

- 在事件入库或报告准备阶段计算并保存全量统计快照。
- 增加协议解析与特征提取层，优先处理 HTTP、DNS、TLS，解析失败必须有明确状态。
- 增加重复分组、证据评分、请求/响应关联和历史趋势计算。
- 重构工程师对话和自动分析的 prompt 构造，使其输入结构统一、字段有来源、裁剪可解释。
- 增加只读的输入预览接口，返回各区块字符数、估算 token、保留/压缩/排除数量和原因；预览不得调用模型或写库。
- 输出 `input_manifest`，说明全量扫描范围、分组数量、关键证据数量、未知证据数量及省略原因。

### 前端

修改范围限定为 `vulnscan-frontend/apps/web/src/views/ly/**`、`api/ly/**` 和必要的 `utils/**`：

- AI 助手区域显示等待时间、预估区间、超出预估和接近超时提示。
- 发送前调用只读预览接口；等待提示使用当前模型和本地成功耗时样本计算区间。
- 不显示虚假的百分比或剩余秒数；流式接口未提供内部进度时，提示必须说明“仅供参考”。
- 报告和命中明细页面继续读取完整事件数据，不显示模型裁剪结果来代替明细。
- 可选增加“本次模型输入”折叠面板，展示输入区块、字符数、估算 token、样本数量和裁剪说明，不展示密钥。

### 不在范围内

- 不删除、覆盖或迁移已有 `occurrences`、原始报文、证据附件索引。
- 不对未授权流量实施 TLS 中间人解密。
- 不让大模型猜测不可解密载荷的明文。
- 不修改 `circular/`、`asset/`、`scanrunner/` 等无关模块。

## 3. 全量分析结果

所有命中记录先参与确定性计算，结果写入事件上下文或独立统计表。至少包括：

- 命中总数、首末时间、持续时间、每分钟/五分钟频次和峰值窗口；
- source、target、端口、协议、方向、会话数量及其分布；
- 请求/响应数量、包数、总字节数、平均/分位包长、重复率和熵；
- 重传、握手失败、异常响应、突增和周期性；
- 同 source、target、规则、IOC 的历史次数、首次出现和趋势；
- 协议解析成功数、解析失败数、加密不可解数；
- 行为分组数量、各组次数、时间范围、共同字段和差异字段。

统计量是模型的直接输入，模型不需要把主要 token 花在重新计数、识别 source/target 或计算趋势上；但模型仍必须基于统计量、协议字段、代表性原始证据和跨记录关系进行二次推理，提出固定规则未预先定义的关联、攻击链假设、异常组合和证据缺口，并明确推理依据与置信度。

## 4. 证据评分与保留策略

评分用于排序，不直接替代威胁等级。建议初始规则如下，权重需通过测试集校准：

| 特征 | 初始分值 |
|---|---:|
| 高危规则或攻击签名命中 | +40 |
| 异常响应、成功迹象或请求/响应不匹配 | +25 |
| 与 IOC、关键资产或历史事件直接关联 | +25 |
| 罕见、唯一或明显偏离组内模式 | +20 |
| 方向异常、短时突增或固定周期回连 | +15 |
| 高熵、疑似外传、重传或握手异常 | +10 |
| 解析失败但行为异常 | +10 |

保留规则：

1. 全量统计和所有行为组摘要必须保留。
2. 每个高分证据必须保留，并尽量同时保留对应请求/响应。
3. 每种协议、方向、IOC 和异常类别至少保留一个代表组。
4. 解析失败、未知二进制和无法解密的流量必须保留有限样本及失败原因。
5. 完全重复的报文只保留代表样本、出现次数、首末时间和内容指纹。
6. 裁剪顺序为：重复原始报文 → 普通背景 → 重复 TLS 握手；不得优先裁剪唯一异常和未知证据。

## 5. HEX、协议解析与 TLS 边界

- 明文载荷先按协议和字符编码解析；解析结果与原始长度、偏移和截断状态一并记录。
- HTTP 提取方法、Host、URL、关键 Header、状态码和响应长度。
- DNS 提取查询名、类型、应答、熵、长度、NXDOMAIN 和查询频率。
- TLS 提取版本、SNI、ALPN、JA3/JA4、证书摘要、握手失败、周期和流量方向；重复标准握手压缩。
- 无会话密钥时标记 `encrypted=true, decryptable=false`，模型不读取无意义的大段密文，但可以结合 TLS 元数据、握手序列、指纹、时序、方向、流量体量及关联明文证据推理隐蔽通信、异常回连和攻击链关系。
- 有授权且可取得会话密钥时，可用端点 key log、TLS 终止点、应用日志或受控代理解密；TLS 1.3/ECDHE 不能仅凭服务器私钥解密。
- 解密或解析失败时，不得让模型从长 HEX 猜测明文；HEX 仅作为有限未知证据样本。

## 6. 模型完整输入上下文

按以下顺序构造，区块名称和来源写入 `input_manifest`：

1. **系统角色**：安全运营助手职责、不得编造、证据分级、未知内容处理、输出格式。
2. **事件基本信息**：ID、类型、规则、严重程度、状态、source/target、协议、时间和资产。
3. **全量统计快照**：次数、频次、持续时间、流量、方向、分布和峰值。
4. **历史趋势摘要**：时间范围、同类事件趋势、首次/最近出现、关联事件和数据覆盖范围。
5. **协议解析摘要**：HTTP、DNS、TLS 及解析失败/不可解状态。
6. **行为分组摘要**：每组次数、时间范围、共同特征、差异、指纹和异常分数。
7. **关键证据**：高分证据、请求/响应关联、必要的明文或短 HEX 样本。
8. **未知证据**：解析失败原因、方向、时间、长度、会话和有限 HEX。
9. **威胁情报**：IOC 值、来源、置信度、标签、有效期和关联关系；测试数据必须标注。
10. **已执行处置**：任务、动作、命令、结果和完成状态。
11. **历史对话**：最近相关用户问题和 AI 回复；保留结论与未解决缺口，限制总长度。
12. **输入完整性说明**：扫描总数、分组数、压缩数、保留数、未送入模型的类别及原因。
13. **当前问题**：本轮工程师请求，只出现一次。
14. **输出要求**：报告章节和安全判断约束。

推荐 16K 上下文的初始预算：输入约 10K token，输出上限 6K token。裁剪前后必须记录估算值；估算只用于预算，不作为上游计费量。

## 7. 接口与数据约定

建议增加：

```text
POST /api/traffic/engineer-chat/estimate
```

请求包含 `event_id` 和当前问题。响应至少包含：

- 模型、超时配置和输出上限；
- 总输入估算 token；
- 各区块字符数、估算 token、记录数；
- 全量记录数、分组数、关键/未知/压缩数量；
- 裁剪原因和 `is_estimate=true`。

估算接口和真实发送必须复用同一 prompt 构造函数。若估算和发送之间新增了对话历史，应在响应中标注上下文可能变化。

## 8. 测试方法与验收标准

### 单元测试

- 全量统计：频次、source/target、时间窗口、方向、包数和字节数与手工结果一致。
- 分组压缩：完全重复记录合并后次数、首末时间和总量不变。
- 评分排序：唯一异常、异常响应、未知报文优先于普通重复记录。
- 请求/响应关联：配对正确，缺失响应被标为缺口。
- 协议解析：HTTP、DNS、TLS ClientHello、解析失败和截断输入均有预期结果。
- TLS：无密钥时不产生伪明文；有测试 key log 时能解出固定测试样本。
- Prompt 估算：预览不调用模型、不写消息；预览和实际发送的系统提示、区块顺序和 token 估算一致。
- 原始数据不变：构造 prompt 前后事件上下文和明细字节完全一致。

### 集成测试

- 用 188 条本地演示明细验证：全量扫描统计正确，重复流量压缩，关键和未知样本均保留。
- 用包含 HTTP、DNS、普通 TLS、异常 TLS、未知二进制和单条异常利用请求的固定 fixture 验证筛选结果。
- 断开 LLM 服务、延迟 65 秒、延迟超过预估和达到超时上限，检查前端提示、按钮状态、错误消息和重试行为。
- 连续发送同一问题，确认不能重复提交；切换事件或关闭弹窗，确认计时器、预览请求和模型请求清理。
- 前端命中明细弹窗仍显示全量记录、载荷和 PCAP 链接，不受模型裁剪影响。
- 报告生成后检查数据库：只新增消息/总结，事件统计和明细不被修改。

### 回归测试

- `go test ./traffic/...`。
- 前端 `vue-tsc --noEmit --skipLibCheck`，确认本次修改文件无新增错误。
- 本地浏览器验证事件列表、命中明细、事件详情、报告生成、下载报告和页面刷新。
- 对比改造前后的事件列表字段、排序、状态、命中次数、时间和审核状态。

### 验收条件

1. 统计结果来自全量记录，且可由测试 fixture 手工复核。
2. 关键异常和未知证据不会因位置采样被静默丢弃。
3. 重复报文压缩后，次数、时间范围和流量总量保持一致。
4. 无密钥 TLS 不输出伪造明文，解密边界和证据缺口清楚可见。
5. 模型输入清单、估算 token 和裁剪原因可通过接口查看。
6. 页面展示完整明细，模型输入裁剪不影响业务列表和详情。
7. 上游慢响应时，用户能看到等待时间和预估状态，不会误以为页面卡死或重复提交。
8. 现有测试通过，且没有新增与本任务无关的文件或数据变更。

## 9. 实施顺序

1. 固定 fixture 和全量统计结构。
2. 实现协议解析、分组压缩和证据评分。
3. 实现 `input_manifest` 和只读估算接口。
4. 重构两条 prompt 构造链路并补齐 token/原始数据测试。
5. 接入前端等待提示和输入预览展示。
6. 运行单元、集成、回归测试，核对数据库和页面结果。
7. 仅在验收通过后启用新筛选逻辑；保留旧逻辑开关以便快速回退。

## 10. 大模型推理职责（修订）

本任务不把大模型降级为统计结果的改写器。后端负责提供全量扫描后的确定性事实和高价值证据，大模型负责在此基础上完成难以用固定规则穷举的分析，包括：

- 连接多个低风险单条记录，识别完整攻击链、阶段转换和潜在 C2/外传关系；
- 对不同会话、source/target、协议、IOC、时间窗口和载荷特征进行跨记录关联；
- 发现统计字段没有直接标出的异常组合、隐蔽周期、伪装流量和行为偏离；
- 比较请求与响应、明文与密文元数据、历史趋势与当前事件，判断成功迹象或替代解释；
- 对未知/不可解密证据提出可验证的假设、置信度、支持证据和反证需求；
- 明确区分“后端确定性事实”“模型推理结论”“仍需验证的假设”，禁止把推理当作已证实事实。

验收时必须加入“关系发现”fixture：单条记录均不足以定性，但跨记录顺序、时间、方向、指纹或响应关系能够支持攻击链判断；测试要求模型输入保留足够的关联证据，并检查报告是否引用具体证据而非只复述预计算统计。

## 11. 报告输出硬性要求

报告生成链路的最终报告必须包含以下字段或章节，不得只输出泛化处置建议：

```text
危险攻击概率：<0–100%，整数或一位小数>
概率等级：低 / 中 / 高
概率依据：支持该概率的主要证据、反证和权重判断
关键证据：按证据编号列出时间、来源、目标、协议、解析字段、行为关系和数据来源
攻击链/关联分析：跨报文、跨会话、时序和历史趋势中由模型发现的关系
替代解释：误报、正常业务或其他合理解释
信息缺口：尚未取得或无法确认的证据
建议处置：按优先级给出可执行动作
```

“危险攻击概率”是研判概率，不是业务规则命中率、频次比例或统计置信区间。模型必须说明：

- 概率对应的定义，例如“该事件属于真实恶意攻击或攻击活动，而非误报/正常业务的概率”；
- 支持概率的关键证据编号；
- 降低概率的反证或替代解释；
- 未解密 TLS、未知二进制或缺失响应对判断的影响；
- 概率为模型研判结果，不替代人工审核，也不表示已经证实入侵。

关键证据必须可回溯到事件明细或业务统计快照，至少包含证据时间范围、source/target、协议/会话标识、解析结果或无法解析原因。报告不得把模型虚构的日志、资产、进程或处置结果作为证据。

测试必须检查概率格式、范围、依据和证据编号；当输入相同而证据变化时，报告概率和依据应发生合理变化；当只有统计量而没有高价值证据时，模型必须降低置信度并列出信息缺口。

## 12. 证据确定性与禁止臆测（硬性要求）

报告必须以可回溯证据为中心。任何事实性结论都必须引用一个或多个证据编号，证据能够回溯到原始命中明细、协议解析结果、全量统计快照、历史记录或已落库的处置记录。

### 必须遵守

- 只陈述输入中能够直接证明或由明确计算规则得到的事实。
- 模型推理必须写出推理链：前提证据 → 关联关系 → 得出结论；不能只给结论性形容词。
- “危险攻击概率”必须说明支持证据和反证；概率不是为了填满字段而虚构的精确数字。
- 证据不足以支持攻击性质、攻击成功、攻击者身份、资产影响或处置结果时，省略该结论，或明确写“无法确认”，同时列出缺失的具体证据。
- 未解析的 HEX、不可解密 TLS、缺失响应、模拟 IOC 和样本外推都不能被表述为已确认事实。
- 不得使用“可能是”“疑似存在”“大概率”等模糊措辞替代证据。如果确实需要保留待验证判断，必须改成结构化假设，包含：假设内容、支持证据、反证、置信度、验证动作。
- 不得编造日志、进程、域名归属、漏洞利用成功、攻击者组织、资产重要性、用户身份或已执行动作。
- 报告中所有“已完成/已发现/已确认/未发现”都必须有对应数据来源；没有来源则不写。

### 结论分级

报告将结论分为三类并使用固定标签：

1. **事实**：可由数据直接确认，必须列证据编号。
2. **推理**：由多个事实关联得出，必须列推理链和置信度。
3. **待验证假设**：证据不足但值得验证；若用户未要求假设分析，可以直接省略，只保留信息缺口和验证动作。

### 验收测试

- 构造“只有普通 TLS 握手、无 SNI/IOC/异常时序”的 fixture，报告不得声称存在攻击或编造攻击者信息。
- 构造“有异常请求但无响应”的 fixture，报告不得声称攻击成功，只能报告请求事实和成功性证据缺口。
- 构造“HEX 无法解析且无协议元数据”的 fixture，报告不得猜测载荷内容。
- 构造“模拟 IOC 明确标记为 LOCAL-DEMO”的 fixture，报告不得将其作为真实威胁情报或封禁依据。
- 对每条报告结论检查证据编号可在输入清单中找到；无证据编号的事实性句子视为失败。
- 对同一事实缺少证据的场景，允许报告更短或省略结论，但不得用模糊语言填充篇幅。

## 13. 证据回溯必须精确到明细记录

报告中的关键证据必须定位到事件中的具体命中明细，不能只引用“该事件”“该会话”或“该分组”。每条保留给模型的明细都必须在上下文中拥有稳定的证据 ID。

### 明细证据 ID

证据 ID 至少由以下部分组成：

```text
E-<event_id>-O<occurrence_index>
```

其中 `occurrence_index` 是事件 `occurrences` 数组中的稳定序号。若同一明细存在请求/响应拆分、协议解析结果或附件，还要使用子证据 ID：

```text
E-<event_id>-O<occurrence_index>-REQ
E-<event_id>-O<occurrence_index>-RESP
E-<event_id>-O<occurrence_index>-PARSED
E-<event_id>-O<occurrence_index>-PCAP
```

压缩重复记录时不能丢失明细范围。分组证据必须同时列出：代表明细 ID、覆盖的原始明细 ID 列表或连续范围、压缩记录数、首末时间和指纹。例如：`representative=E-demo-O17; members=O17,O18,O19...; count=42`。

### 每条明细必须带的回溯字段

- `evidence_id`
- `event_id`
- `occurrence_index`
- 命中时间、捕获时间和会话首包时间（有则提供）
- source、target、端口、协议和方向
- 会话或流 ID、包序号（有则提供）
- `wire_bytes`、`packets`、捕获长度、线缆长度和截断标志
- 原始明细字段路径，例如 `context.occurrences[16]`
- 解析状态：`parsed`、`partial`、`encrypted`、`unknown` 或 `failed`
- 解析出的关键字段及字段来源
- 触发的特征、异常分数和筛选原因
- 请求/响应关联的证据 ID
- PCAP 证据索引（存在时）

### 报告关键证据格式

报告必须使用可核对的证据条目，不接受只有自然语言的“关键证据”段落：

```text
[E-<event_id>-O<index>-PARSED]
明细：第 <index> 条，时间 <time>，source <src> → target <dst>，协议/方向 <protocol/direction>
问题：<该条明细具体存在的问题，必须基于字段>
依据：<字段路径和值，例如 payload_text、dns_qtype、tls.sni、response.status>
关联：<对应请求/响应、同组明细或历史证据 ID>
支持命题：<这条明细能够支持的具体命题>
不支持命题：<不能由这条明细推出的结论>
证据作用：<关键行为证据/成功性证据/排除性证据/背景统计>
```

“问题”必须具体，例如：`DNS TXT 查询，子域名熵值高且 57 条中该模式占 56 条`、`HTTP 请求命中规则但未找到对应成功响应`、`TLS ClientHello 的 SNI 与历史 IOC 关联`。不得写成“流量可疑”“存在风险”等无证据描述。

一条证据是否为“关键证据”，取决于它是否能直接支持报告中的某个明确命题，而不是是否能单独证明完整攻击成功。应区分：

- **行为证据**：证明发生了某种异常或攻击样行为，例如高熵 TXT 查询、规则命中、异常回连；可以作为攻击性质和危险概率的组成证据，但不能单独证明入侵成功。
- **成功性证据**：证明请求产生了成功响应、命令执行、权限变化、数据回传或其他结果；只有这类证据才可支持“攻击成功”结论。
- **排除性证据**：证明某种解释不成立或降低概率，例如请求无响应、TLS 为普通重复握手、终端核查未发现持续进程。
- **背景统计**：提供频次、趋势和体量，通常不能单独作为攻击证据，但用于解释行为规模和持续性。

因此，“支持持续性 DNS 隧道行为，但不能单独证明攻击成功”可以作为**行为证据**，不能作为攻击成功的证据。报告必须把它放在“行为证据”下，并由其他明细继续寻找成功性证据；如果找不到，应明确报告“未发现攻击成功证据”，而不是把行为证据升级成成功结论。

如果某个结论需要多条明细，必须列出全部关键明细 ID 或明确的连续范围，并说明每条记录在推理链中的作用。报告不得引用模型没有看到的明细。

### 相关验收测试

- 生成报告后，解析报告中的每个证据 ID，必须能在输入 `input_manifest` 和原始 `occurrences` 中找到唯一记录。
- 任意证据 ID 不存在、索引越界、时间/source/target 与原记录不一致，测试失败。
- 报告中的“问题”必须引用至少一个实际字段路径和值；只有泛化形容词时测试失败。
- 请求/响应关联测试必须同时显示关联证据 ID，缺少响应时明确写“未找到对应响应”，不得写攻击成功。
- 重复分组测试必须验证代表证据和成员范围可展开回原始明细，且压缩不改变次数和统计量。
- 证据被 token 裁剪时，必须保留证据索引和裁剪说明；模型不得引用未送入上下文的记录。
