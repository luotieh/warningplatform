- 状态：已按授权进行本地核心代码实施；生产迁移、发布及 P7 完整验收未执行。实现对应关系、已通过测试与剩余门槛见 [本地实施结果](2026-09-18-traffic-aggregation-local-implementation.md)。本文保留原计划验收标准，不以本地构建代替生产验收。

## 1. 目标与范围

最终效果：重复上报只计一次，真实重复行为分别保留；同一活动按发生时间正确归并；所有新增有效命中可分页回溯；列表、报告与统计接口使用同一版本的数据；历史无法恢复的统计明确标注完整性。

本次包含：接收幂等、全量命中存储、聚合生命周期、量化统计、明细接口与证据跳转、两条模型调用链的数据接入、历史修复工具、迁移及部署回退。

本次不扩大到：双向五元组聚合策略、攻击检测规则、模型协议/超时设置、TLS 解密、自动处置、无关业务模块。保留当前有向 `src_ip + dst_ip + event_type` 分组，反向流量不在本次自动合并。

## 2. 已核验基线与风险

9 月 18 日只读检查的线上镜像为 `warning-platform:v2.1-20260916-c62d03f-llm-protocol`，容器健康。以下是历史数据现状，不代表已对新版实时写入做端到端验证。

| 核验项 | 结果 | 对应修复 |
|---|---|---|
| 列表接口与数据库 | 84 条事件，ID、次数、载荷、收敛状态一致 | 不在前端掩盖数据问题 |
| 重复明细 | 27 条事件存在完整记录重复，包含相同抓包时间和包序号 | 接收端持久化幂等 |
| 双份计数 | `evt-f6e91699af36a428186f3a2e614b344a` 为 184913 / 184713 | 唯一统计来源和事务 |
| 相邻生命周期 | 51 对同键事件发生时间间隔不足 30 分钟或重叠 | 按发生时间归属，处理补传；逐条核验，不能直接全部合并 |
| 归档日期 | 12 条不等于北京时间最后发生日期 | 时间口径和历史校正 |
| 明细截断 | 两条大事件仅剩 200 条，峰值依赖截断样本 | 全量存储和全量窗口统计 |

代码核验：

- `ProcessLyEvent` 使用进程内锁，直接推送路径没有持久化命中去重；`RunSyncOnce` 的去重只覆盖同步路径。
- `mergeOccurrenceLocked` 每次接收直接加一，`maxOccurrences=200` 会丢失早期明细。
- 收敛判断同时使用系统当前时间，迟到的历史命中可能持续被拆成新事件。
- `quant_stats` 与 `occurrence_count` 分别维护；峰值来自截断后的 `occurrences`。
- `chat_context.go` 以 `E-<eventID>-O<数组下标>` 生成证据 ID；数组移动、截断后不能保证历史引用稳定。
- 采集端文档称 `event_id` 是“同包同规则的稳定 ID”，且 `packets/bytes/wire_bytes` 是流累计值。必须核实实际节点版本；不能把累计快照逐条相加当作真实流量。

## 3. 固定业务规则

### 3.1 命中、报文、重复上报分别计量

1. 一次有效命中 = 一次独立检测结果；同一报文命中两个规则，是两次规则命中。
2. 重试传输不产生新命中，不累计字节，不延长活动时间，不触发额外报告。
3. 相同载荷发生于不同包/时间/会话时分别保留；不得仅靠 payload hash 去重。
4. 多节点各自观察到的命中按节点分别保留；本次不宣称具备跨节点物理报文去重能力。
5. 列表继续称“命中次数”，不得自动等价为攻击次数、会话数或报文数。

### 3.2 幂等键与异常上报

- 优先：`source_namespace + device_id + 稳定的源命中ID`；键的规则与版本持久化。
- 只有验证源 ID 语义后才能启用该策略。源 ID 若是聚合 ID 或可复用 ID，改用经验证的完整命中身份。
- 兼容键：节点/采集会话标识、微秒级抓包时间、包序号、五元组、规则或 IOC 身份、必要载荷摘要。接收时间不进入键。
- 身份字段不足时，不用宽松 hash 静默删数据：持久化到待核验接收区，返回明确状态，暂不计入权威统计，并记录原因。
- 同一幂等键、相同检测身份：作为重试成功应答。可变传输元数据不制造新命中。
- 同一幂等键但检测身份/不可变证据冲突：保留冲突记录及原始证据，进入核验；不覆盖已有命中、不重复累计，不无限触发重试。
- 数据库存储失败返回失败，由采集端重试；鉴权失败仍返回 401。原推送响应字段保持兼容，新增 `duplicate`、`ingest_status` 等状态。

### 3.3 时间与生命周期

- 时间归一化函数同时支持 `capture_time`、`packet_time_usec`、文档中的 `event_time`、`occurrence_time` 和旧 `time`。按节点 schema 明确优先级：优先有效高精度发生时间，记录来源与字段冲突。
- 内部 UTC、微秒精度；UI 和归档业务日期统一 Asia/Shanghai。无时区旧字符串按既有北京时间约定解析。
- `occurred_at` 和 `received_at` 分开；缺失/非法/明显异常发生时间的上报进入待核验状态，不能默认用 now 充当攻击时间。异常时间阈值在阶段 0 用节点时钟样本确定并记录。
- 同键命中按发生时间排序，相邻间隔 `< 30 分钟` 属于同段，`>= 30 分钟` 分段。连接关系具有传递性，不是固定半小时桶。
- 当前时间仅决定该段是否已静默收敛，不能阻止历史命中加入所属时间段；报告生成、审核、重试均不延长窗口。
- 归档日期 = 有效最后发生时间的北京时间日期。接收晚、分析晚不改变这一定义。

### 3.4 迟到数据、桥接合并和历史身份

- 新命中到达时查询同聚合键全部相关时间段，而非只读 `event_maps` 最新一条。
- 仅连接一个时间段：加入该段并重算受影响统计。已归档段允许受控数据修订，保留修订审计；按修正后的末次时间重新判断收敛/归档。
- 不连接任何段：新建时间段；历史段可直接处于已收敛状态。
- 同时连接多个段：新建修订记录，选择最早创建的事件作为 canonical event（同创建时间以 ID 排序），其他 ID 保留为关联历史身份。
- 列表默认展示 canonical event 一行；旧链接仍能访问原报告、审核及通报记录，并提示当前关联事件。明细身份不变，记录每次归属变化。
- 不删除或无痕迁移聊天、报告、审核、通报；多个事件既有审核/通报状态冲突时，标记“合并后待复核”，不得继承为自动通过或触发处置。
- 旧报告保留原数据版本，新数据到达后标记已过期；同版本分析任务去重，避免每个迟到包触发一次模型调用。
- 历史数据不完整的事件先保持 legacy 状态；不能仅凭首末时间区间确认其中不存在 30 分钟空档，也不能直接将其与新完整事件混成“全量已核验”。

## 4. 数据模型与事务设计

以下名称为拟新增表/字段，实施时遵循现有迁移框架；必须提供显式、带版本的迁移，不靠 `CREATE TABLE IF NOT EXISTS` 完成旧表升级。

| 存储 | 最小职责与索引 |
|---|---|
| `traffic_event_hits` | 有效原始命中：稳定 hit_id、源身份、dedup_key/version、aggregate_key/version、occurred_at、received_at、节点/规则/IOC/方向/五元组、payload/证据引用、输入摘要；dedup_key 唯一，身份键使用二进制或大小写敏感比较；索引 aggregate_key+occurred_at+hit_id |
| `traffic_event_hit_memberships` | 命中到事件的当前归属及版本；一个有效命中只归属一个当前 canonical event；索引 event_id+occurred_at+hit_id |
| `traffic_event_segments` | 聚合时间段、首末时间、canonical ID、状态和版本；aggregate_key+first/last 时间索引；`event_maps` 不再充当唯一历史归属依据 |
| `traffic_event_stats` | 每个事件每个数据版本的权威统计快照：次数、首末、分布、流量口径、峰值、质量状态、schema_version；已发布快照不可覆盖 |
| `traffic_ingest_receipts` | 待核验/身份冲突记录和接收状态；重复正常上报只维护计数及最后接收时间，避免重复保存大载荷 |
| `traffic_event_revisions` | 合并、成员变更、历史修复前后值、输入清单摘要、操作者、批次与回退依据；保存旧 ID 关联和证据别名 |
| `traffic_event_outbox` | 提交后统计重建/报告失效等任务；任务键包含事件、数据版本、类型并唯一；支持重试、去重和进程重启恢复 |
| 现有 `events` 扩展 | 数据/统计版本、canonical ID、统计完整性和报告过期状态；保留 context 兼容投影及现有业务关联 |

原始命中一经确认身份，证据不可被后续重试覆盖。大载荷使用独立载荷表/现有受控文件引用，与列表查询分离；新增命中不得再次截断到 200 条。已有上游截断状态必须如实保留，不能宣称恢复了未采集字节。

事务顺序：

1. 验证身份与时间，在事务中创建/锁定聚合键行；跨进程依赖 InnoDB 锁和唯一约束，进程内 mutex 只作优化。
2. 插入命中并处理唯一冲突；重复接收返回已有结果，不产生聚合副作用。
3. 锁定相关时间段，确定归属/桥接；多事件锁按固定顺序获取，死锁采用有限重试。
4. 写入成员关系、数据版本、确定性统计变更、context 兼容投影、修订与 outbox 后提交。任一步失败全部回滚。
5. 提交后执行异步任务；失败可恢复，不允许出现“命中已接收但任务因进程退出永久丢失”。网络调用和 LLM 调用不放在事务内。

大段合并和峰值重建采用后台计算，使用固定数据版本的快照及稳定游标扫描。全部计算完成后原子发布快照；计算期间所有消费者一致使用上一已发布版本并显示“统计更新中”，不能将新次数与旧峰值混用。首次尚无可发布快照时显示待计算，不伪造 0。

兼容投影中的 `occurrence_count`、`quant_stats` 必须由同一个已发布快照生成；禁止独立累加。调度器、归档器、手工刷新必须遵守同一事务/版本协议。

## 5. 统计口径

- 有效命中数：已确认、去重后的 hit 数；按规则和 IOC 分类，同包多规则不冒充多个物理包。
- 原始上报次数、重试次数、有效命中数、已保存明细数分开返回。
- 五分钟峰值：对该版本全量有效命中按 `(occurred_at, hit_id)` 扫描，滑动窗口采用半开区间 `[start, start+300s)`，精确到微秒；不得以 200 条样本或分钟桶近似值冒充精确结果。
- 平均频率按已定义发生窗口计算；首末相同导致持续时间为 0 时返回不可计算及原因，不返回误导性的 0 次/分钟。
- `packets/bytes/wire_bytes` 先标注上游单位是单包、流增量还是流累计快照。
- 单包数据：按可信报文身份去重后求和；流累计快照：按节点+会话/采集周期+方向归属，只累加有效高水位增量，处理乱序、计数器重置和同流多规则重复观察。
- 累计快照跨多个事件/时间段时，不能把全流总量重复归给每个事件；只有能确定增量发生区间时才归属，否则显示关联会话观测量及范围限制。
- 缺少可靠 flow/session 身份或初始基线时，不宣称得到真实总流量；保留“上报观测量”及 `volume_quality`，真实流量字段可为空，排序时未知值排末尾。不得为保持数字好看继续错误求和。
- 来源/目标/规则/IOC 分布从全量 hit 构造，后续命中的规则、域名等不能仅继承第一条事件 context。
- 数据质量最少区分 `verified`、`partial`、`unverified`、`rebuilding`，并返回原因、已保存数量、源声明数量和截断信息；质量按指标表达，不能用一个“已核验”掩盖流量未知。

## 6. API、前端与报告接入

### 6.1 查询与兼容

- 保留 `/api/traffic/events/list` 的现有字段、默认所有时间、分页、筛选和排序。
- 增加数据版本、统计版本、完整性、canonical ID、报告过期状态；排序和展示从同一发布快照读取。
- 新增 `GET /api/traffic/events/detail/:eventID/occurrences`：稳定游标分页，支持时间和身份筛选，返回 snapshot_version、items、next_cursor、可用数量和完整性。按固定快照翻页，迟到数据不造成漏页/重复页。
- 新增 `GET /api/traffic/events/detail/:eventID/occurrences/:hitID`：精确查询证据、解析字段、采集身份和附件引用；校验事件关联和权限，不能借 ID 越权读取其他事件。
- 旧 `occurrences` 字段可暂保留最多 200 条兼容预览，但必须标明 preview/total/has_more；新 UI 和报告不能继续将它视为全量。
- 新数据证据引用使用不可变 hit_id；旧 `E-事件-O序号` 只能通过对应报告快照/冻结迁移映射解析。无法确认旧索引对应关系时显示“历史引用无法核验”，不得指向当前相同序号的另一条报文。
- 保持 PCAP 原链接和 ZIP 功能；新增稳定命中到证据引用的映射，并保留旧附件索引别名。

### 6.2 UI

- 命中明细弹窗从分页接口读取，支持通过 hit_id 精确定位；数字序号仅是显示顺序，不能作为证据主键。
- 列表/详情显示有效命中次数、数据质量及必要的“统计更新中”提示；大事件不再只能看到最近 200 条。
- 历史不完整事件显示“已保存 X 条明细；原记录宣称 Y 次，未核验”。
- 合并事件显示来源事件关联，旧报告仍可查看；报告过期时提示基于旧数据版本，可手动重新生成。
- 保留登录跳转、生成报告、停止请求、审核、通报、归档和默认时间筛选行为；这些作为回归测试，而非新增业务改造。

### 6.3 模型上下文

- 报告流水线与聊天不是同一个业务入口；二者共享新的 EvidenceSnapshotProvider，统一取得固定版本统计、完整性、全量扫描结果及稳定证据引用。
- 替换只遍历 `context.occurrences` 的数据来源，采用分批扫描全量 hit 后按现有证据选择规则压缩上下文；不把几万条原始记录直接塞入 prompt。
- 保存输入 manifest：数据/统计版本、实际扫描数量、可用与缺失范围、选中 hit_id、模型输入压缩数量及原因。历史 partial 数据禁止生成“已扫描全部原始明细”的错误说明。
- 报告生成期间到达新命中：本次使用原固定快照完成，结果标注其版本并在必要时标记过期，不混入新版本统计。
- 报告关键证据 1、2、3 编号，每项引用稳定 ID 并说明具体问题；危险攻击概率仍属于模型判断，不能把频次直接转换为概率。保留现有禁止编造处置和攻击成功的约束。

## 8. 历史数据修复策略

工具默认 `audit/dry-run`，不得启动应用即自动全量重写。

1. 保存原始事件 context、统计、时间、映射、报告引用及关联状态的可恢复快照，附数据库备份、校验和和修复批次 ID。
2. 明细导入时保留原数组位置及旧引用映射；历史去重要求可信包身份/规则身份，不因相同 payload 直接去重。
3. 区分三类：有完整且身份可核验的命中；可从可信采集记录补齐的命中；只剩截断样本、身份不足或时间含糊的事件。
4. PCAP 仅能证明报文存在，不能自动重建原检测规则/IOC 命中、完整上报次数；只有检测版本和记录对应关系可验证时，才用于恢复权威命中。
5. 前两类重建时间段及统计，生成前后差异预览；第三类保留历史宣称总数、已保存样本和完整性标签，不改造成虚假的精确统计。
6. 184913 次事件不得改成 3 次；184913 与 184713 差值不得凭猜测补齐。归档日期仅在发生时间可靠时修正。
7. 对 51 对相邻事件逐条核验，只合并可证明属于同段的事件；既有审核/通报冲突进入待复核。
8. apply 校验 dry-run 清单摘要及数据版本；有并发变化则跳过/重新预览，不能覆盖新写入。分批事务、限速、可暂停、失败可续跑。
9. 不批量自动调用模型；把受影响报告标记过期，后续按需求生成。保留旧报告版本和依据。
10. rollback 只撤销本批次且版本仍匹配的派生变更；有后续新数据的事件采用补偿重建，不能删除新增命中或覆盖后续审核。

## 10. 发布、观察与回退

1. 首先构建一个具备新数据读取/兼容投影、持久化接收与保留原始命中能力的兼容版本，验证旧库迁移；它作为后续回退目标。不能把只含旧逻辑的镜像视为启用新写入后的安全回退版本。
2. 全量新增存储会增加空间，发布前根据真实大小和峰值吞吐确定容量及保留策略；本次不默认自动删除证据。容量不足时停止接收并返回可重试失败、告警，不成功应答后丢弃数据。
3. 备份数据库及配置，验证恢复；保存旧镜像和新镜像 SHA。迁移使用数据库内版本/特性状态，无需覆盖原 TOML，既有配置文件和 Docker 挂载保持原样。
4. 镜像在隔离数据库/隔离端口验证，不能两个容器同时连接生产库运行接收、同步或归档调度器。
5. 准备维护切换窗口：确认采集端可持久排队重试；暂停写入入口和旧调度器、排空在途请求，执行增量迁移和既有身份种子导入后启用新版。无法证明的旧 ID 不作为强去重种子，防止误删真实数据。
6. 切换后恢复接收，在真实数据上观察；不发送合成事件到生产。检查成功/重复/冲突/待核验数、统计版本滞后、outbox 积压、活动段冲突、归档日期偏差、数据库空间。
7. 增量接入至少覆盖一个完整收敛窗口（30 分钟）及一次归档任务；没有真实新流量时明确标注“线上接入待验证”，不能仅凭容器健康宣称完成。
8. 历史修复另执行：先发布 dry-run 差异清单，经审阅后按批 apply；不与应用启动绑定，不一次全库自动合并。
9. 回退新增功能：暂停入口并排空后，回到第 1 步兼容版本，保留所有新 hit 和迁移表，继续可靠接收或明确排队；禁用有问题的派生任务，待修正后按原始命中重放。禁止两个聚合写入器同时运行。
10. 绝不能直接恢复上线前全库备份覆盖运行后的数据库，这会丢新增事件、聊天和审核。严重故障按数据增量/日志进行恢复；派生数据由修订与原始命中补偿重建。降级到不认识新格式的更旧镜像只允许在停止写入并验证兼容性后进行。
