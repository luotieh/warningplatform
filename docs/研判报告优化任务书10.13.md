# 研判报告优化任务书10.13

日期：2026-10-13  
性质：Codex实施任务书；本轮仅制定任务书，不开始代码实施。  
实施基线：以实施时GitHub提交、工作区和180实际运行版本为准；本次编写时已部署版本为`0c59bbc2a074c8759165559fdb7348992ef7cf38`。

## 一、目标

看清模型能接收和输出多少内容、真实事件有哪些证据能正常运行、证据归一前后发生了什么、模型实际收到什么、研判概率依据是什么。确保每份成功生成的正式报告包含研判概率，且事件列表同步显示同一份报告的概率。

本次重点是可观测性、报告专用容量配置和概率输出契约，不重做证据算法、权重体系或报告业务流程，不承诺通过增加日志直接提高报告质量。

## 二、范围与边界

允许修改：

1. 正式报告生成路径及其专用日志，包括自动生成、报告刷新按钮、聊天中明确要求生成／重新生成正式报告的入口。
2. 报告专用输入预算、输出上限和上下文窗口参数的读取、验证与调用传递。
3. 报告提示词、与必填概率对应的现有输出校验，以及已有报告保存、事件概率发布路径的必要一致性修复。
4. 配套测试、日志说明、真实事件核验工具和核验记录。

禁止修改：采集端、数据库结构或索引、告警检测／聚合／审核、证据算法前提、证据判断阈值、证据权重值、其他业务模块、前端，以及全局模型配置的既有调用行为。普通聊天与语义槽位调用的预算和行为保持不变；共享函数通过显式报告参数隔离。

对用户所说“1、2、3是日志任务；4是提示词任务”，按以下边界执行：

- 第2、3项严格只增加观测、记录与核验，不调整证据结果、选择、归一或权重。
- 第1项除日志外，明确允许新增报告专用容量参数；参数未显式启用时保留原有容量行为。不得擅自提高线上上限。
- 第4项优先调整提示词并复用现有校验／发布流程；已有规则允许`null`时，必须同步收紧概率契约。仅改提示词不能作为完成标准。
- 若概率丢失涉及范围外展示逻辑，记录具体证据和位置，不擅自修改前端。

保留无关未提交改动，只提交本任务文件。未经本任务实施阶段另行授权，不推送、不部署、不触发模型容量压力探测，不恢复已停止的独立报告评审。

## 三、开始实施前必须核对

读取适用仓库说明，核对当前工作区、分支、提交、180容器镜像和报告构建版本，建立任务清单与文件范围清单，然后直接实施范围内工作。

重点核对以下事实，不将代码注释当成线上能力证明：

- 输出`max_tokens`已有配置入口，代码默认6000；报告输入和总提示词预算已有估算值。明确它们的计量口径及实际生效位置。
- 正式报告结构化输出已有`probability`、`probability_reason`及证据引用校验，当前允许部分情况返回`null`。
- 正式报告存在保存、渲染和事件概率发布路径；追踪实际列表字段，不预设概率一定来自正文正则提取。
- 聊天生成正式报告已接入正式服务；普通追问仍是聊天服务，不纳入“每份正式报告必须带概率”的约束。

## 四、任务1：模型容量与报告专用配置

### 4.1 区分四个量

1. 模型／服务端允许的总上下文窗口：输入、输出及协议／推理等占用共享的总容量，具体口径以当前模型服务实际协议为准。
2. 报告输入预算：完整system、user、消息封装及调用中其他输入内容的预算。
3. 报告输出上限：调用请求实际传递的输出token上限。
4. 实际用量：服务返回的输入、输出、缓存和推理用量（仅记录服务实际提供的字段）；缺少usage标记为不可获取，不填0冒充实际值。

20 tps记录为已有观测的输出速度，不作为上下文容量依据。估算token、字节、字符和服务端usage分别记录，不混用。

### 4.2 报告专用参数

通过后端现有配置机制新增或明确以下报告专用参数，最终名称遵循仓库规范：

- `report_input_token_limit`：完整输入预算。
- `report_output_token_limit`：输出上限，初始保留现有可行6000。
- `report_context_window_tokens`：已核实的总上下文窗口；未知时明确标为未核实，不编造窗口值。
- `report_token_safety_margin`：为封装、估算偏差及适用的其他占用预留空间，记录来源和取值。

配置校验：数值必须有效；已知窗口时，输入预算＋输出预算＋适用的额外预留不得超出窗口。定义未知窗口下的行为，保留兼容默认值并记录“容量尚未核实”，不能因未核实就允许无限增大。

正式初次生成与格式纠正调用使用同一配置规则；记录实际生效值、默认／显式来源、配置摘要、模型标识和调用协议，不记录密钥。

### 4.3 从6000逐步核实

分别核实输入与输出容量，不能把`max_tokens=6000`当成输入上限，也不能把输入、输出各6000称为总窗口6000。

实施配置和工具后，在明确授权的受控验证中，从输入6000这一测试档位起，按6000→8000→10000等档位逐步验证；档位服从服务端已知窗口。输出先保留现有6000，后续单独验证，不同时增加输入和输出导致无法定位失败原因。

用真实报告材料构造容量验证输入，不删除核心事实以让测试通过，不将重复无意义填充当成报告能力验证。检查响应、usage、finish_reason、完整JSON、证据引用、耗时和超时；首个容量失败即停止提高，记录已验证范围和失败边界。不得触发无授权的持续压力测试。

只说明“该模型、该配置、该测试范围已验证”，不能将一次成功推断为模型官方最大窗口。配置扩大后若时间预算不足，记录具体限制，不偷偷修改全局超时。

## 五、任务2：证据可用数量、归一与概率依据日志

### 5.1 完整证据清单

核对原设计59项事实规则与23个语义槽位，以及后续新增观察项，分别统计，禁止把新增统计项混算为原59项。语义槽位类型数与实际任务实例数分别列出。

为每个条目建立材料依赖表：规则／槽位编号、所需字段、真实读取位置、绑定／时间窗／样本要求、默认策略、是否依赖其他事实、执行入口和输出字段。

“可用”指在被核验真实事件中：适用、必要材料实际满足、完成算法计算或语义执行、结果通过现有校验，且没有阻止该结果成立的信息缺口。材料齐全但条件未命中的正常负向结果也算完成；仅登记、排队、返回JSON或合成测试通过不算实际可用。

明确区分：

- 不适用：例如纯TCP ACK事件没有HTTP正文，不应期待HTTP规则命中。
- 适用但缺材料／覆盖不足／样本不足：具体标明缺项和发生位置。
- 输入满足但运行失败、预算未执行、输出校验失败、重复实例。
- 已完成：正向命中、有效负向结果、描述性观察、语义解释分别统计。

针对实施时可访问的一组真实事件，先完整登记事件集合及选取依据，覆盖实际存在的主要材料类型；不按最高概率挑样本。输出逐事件清单、至少一例完成的条目集合、所有适用事件均完成的条目集合及分母。不要把某一个事件的完成数当成证据库整体可用数。

### 5.2 每个报告任务的证据日志

保存下列阶段，禁止通过重新计算代替“本次实际使用结果”：

1. 归一前：实际材料供应清单、事实执行结果、语义计划及实际结果、新增观察结果、各自来源与覆盖范围。
2. 归一后：统一编号、原始编号映射、状态、质量、命题、范围、时间窗、指标、来源、依赖、重复关系和非累加关系。
3. 归一后的报告投影／选择：保留、排除、单独作为背景解释、被压缩或预算拒绝的条目及现有原因。
4. 最终送入LLM的证据：编号、事实／指标、引用关系、权重、适用条件及数量。

逐项保留稳定的原始ID→归一ID→报告证据ID映射，使读者能追溯同源证据、同命题重复和历史DNS／通联的区别。归一、选择和最终输入是三个阶段，不能用一个“归一后数量”掩盖后续排除。

### 5.3 权重与概率解释

记录本次实际权重策略版本、每条证据的生效权重、适用条件、证据族／依赖组、重复计证限制、支持／反向／背景角色及概率输出约束。不得借日志任务调整任何权重。

先核实当前是否存在程序化概率计算公式。若当前是“模型在证据和权重约束下给出估计”，如实记录，不生成虚构加减分公式。记录可观察的判断过程：

证据及权重输入→模型结构化支持依据、反向依据和替代解释→概率及概率理由→程序校验→最终发布。

不要求模型提供隐藏思维链，不把自然语言概率理由当成内部计算实录，不声称凭日志证明55与65已精确校准。若存在真实程序评分，记录实际公式、输入、各项贡献和计算输出；评分与模型概率仍需区分。

## 六、任务3：最终LLM输入与调用日志

必须从实际调用边界采集，保存原样发送的system／user内容、消息顺序、事件概览、选中证据、来源目录、范围／时间窗目录、历史关联、对话补充及适用的请求参数；不是另外拼一份“看起来相同”的提示词。

初次报告调用与纠正调用分别编号和记录。记录请求内容哈希、模型、脱敏端点、配置值、估算token、服务实际usage、finish_reason、响应文本、解析和校验结果、耗时、成功或失败阶段。语义调用用同一任务关联信息记录；命中缓存时保存引用及缓存版本，不虚构一次新模型调用。

超过预算而未发出请求时，记录准备好的内容、预算值和拒绝阶段，并明确`sent=false`；不能将待发送内容记为模型已收到。

新增日志不得改变输入选择或压缩策略，不为避免日志体积而截断关键证据。原业务已有截断／排除如实记录。日志不得向客户端泄露完整敏感流量材料。

## 七、统一日志规范：data/repLogs

目录以应用实际工作目录为基准，例如容器`/app/data/repLogs`；实施时明确绝对路径。日期采用Asia/Shanghai，详细时间戳保留时区。

建议结构：

```text
data/repLogs/YYYY-MM-DD/<event_id>/<report_run_id>/
  manifest.json                  # 任务、版本、快照、阶段状态和日志完整性
  material-coverage.json         # 材料供应、缺口及适用性
  evidence-before.json           # 本次事实、观察、语义执行原始结果
  evidence-normalized.json       # 归一结果及ID映射
  evidence-selection.json        # 选择／排除／背景原因
  evidence-weights.json          # 实际权重、依赖与概率约束
  llm-call-01-request.json        # 原样输入及非敏感请求参数
  llm-call-01-response.json       # 回复、usage、解析和校验
  llm-call-02-request.json        # 仅发生纠正调用时存在
  llm-call-02-response.json
  probability-publication.json   # 结构化概率、正文概率及发布核验
  summary.md                     # 可读摘要，含数量、缺项及概率依据
```

字段至少关联：event_id、report_run_id、snapshot_version、analysis_version、报告／总结ID、构建commit、模型与配置摘要、算法／语义／归一／权重版本、入口类型、调用序号、状态及时间。

失败、缓存复用、预算不足、未调用和发布失败均记录；未发生的阶段不填假结果。不同并发任务不得覆盖日志。使用原子写入或明确完成标记，日志应能区分已提交、运行、成功、失败。

日志写入失败不使原本正常的报告业务失败，输出明确可定位的告警并记录可获得的错误信息。避免记录密码、API密钥、认证头、含密钥查询参数和数据库连接凭据。真实报文日志仅供授权内部人员访问。

交付日志保留与磁盘管理办法。日志可配置关闭／过期清理，具体默认值写入说明；清理只处理本目录内已完成任务，不能删除运行中日志或业务证据。

Docker升级时明确日志持久化方式与宿主机映射；本轮文档不直接改变180挂载配置，实施部署时核对已有挂载并将映射变更列入部署说明。

## 八、任务4：成功报告必带概率且同步事件列表

### 8.1 输出契约

概率命题为“本次通信属于恶意活动的研判概率”，不是主机失陷、攻击成功概率。正式报告必须返回0～100整数`probability`及有证据引用的`probability_reason`。

提示词明确：成功报告禁止遗漏概率字段、返回null、用区间／等级／字符串代替整数；正文结论明确展示“研判概率：X%”。保留原五段结构：结论→事件总览→关键证据→风险分析→建议处置。

禁止填默认概率、保底概率、抬高概率、根据事件标题猜测或伪造依据。现有反向证据、同源去重和高概率条件继续生效。

真实材料不足以支撑概率时，任务记录具体失败／材料缺项，不发布一份无概率的新正式报告，不把旧报告标成新版本。此要求保证“每份成功报告有概率”，不意味着“每次请求都必须成功”。

### 8.2 校验与同步

先查清实际链路，复用现有格式纠正及校验，不为拿到概率无限重试、不挑最高概率回答。缺失、null、越界、类型错误、证据不成立时，走现有纠正／失败流程；必要时仅调整与新契约冲突的规则。

结构化概率是唯一来源，同一值用于报告正文、报告记录及事件列表字段；不新增从自然语言正文猜测概率的路径。

生成成功后核验：正式报告概率＝正文显示值＝事件详情／列表接口概率，且对应同一份已发布报告的ID、快照和版本。已有保存顺序出现部分成功时，记录发布失败，不能宣称完成；复用现有事务／状态机制进行范围内必要修复，不新增数据库结构。

失败时保留最近成功报告及其概率，明确新任务失败；禁止清空旧概率、写入临时值或把新失败任务与旧报告拼接为成功结果。

并发和后台自动生成场景不得由较早任务覆盖较新成功报告；核对现有保护并增加相应测试，仅在确有缺陷时作报告专用修复。

## 九、测试与真实核验

必要测试覆盖：

1. 容量参数缺省兼容、有效值、非法值、已知窗口超预算，以及参数仅作用于正式报告调用。
2. 归一前后ID可追溯、同源关系、选择原因、缓存和失败日志、初次／纠正输入准确性、未发送状态。
3. 日志写入失败不阻断业务；日志无密钥；并发任务不覆盖；目录和过期清理边界有效。
4. 缺失／null／越界／错误类型概率触发校验；有效0、普通概率和有依据高概率按现有规则处理；正文与结构化值一致。
5. 保存／发布失败保留旧成功概率；事件列表同步；不同报告版本不串用。
6. 普通聊天、语义调用预算、证据算法和权重不因日志任务改变；聊天生成正式报告仍走统一正式路径。

在获得实际运行核验授权后，对已登记真实事件生成新报告，核对完整日志及实际概率同步。至少覆盖实际存在的DNS材料、TCP通联和多日历史关联；不存在的材料类型如实列为未覆盖，不合成替代真实核验。DNS角色错误属于本轮观察项：定位并记录，不借日志任务修改归因算法。

容器启动、测试JSON返回、合成测试和日志文件存在，均不能替代真实报告与列表概率一致的业务核验。未获得部署／模型调用授权时，明确记录尚未完成的真实核验，不宣称整体完成。
