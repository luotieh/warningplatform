# 报告等待提示与模型输入

更新日期：2026-09-15。以下以报告弹窗中输入“生成报告”的工程师对话链路为准。

## 等待提示

AI 助手区域顶部固定显示等待状态，同时更新当前等待消息：

- 初始显示“已等待 X 秒，预计总耗时 45–90 秒”，注明经验估计。
- 成功请求的耗时按模型服务地址与模型名组成的指纹存入当前浏览器，最多保留最近 20 次；失败或取消请求不计入。
- 有历史样本后，以成功耗时的中位数乘 0.7 / 1.4 作为区间上下界，按 5 秒取整，并受实际模型超时限制。
- 超过预估上界后，显示“已超出预估时间，上游响应较慢，仍在等待模型返回”。接近超时上限时提示避免重复提交。
- 不显示虚构的生成百分比或剩余秒数。当前模型请求为 `stream: false`，客户端不能获知模型内部进度。
- 请求结束、失败、切换事件或卸载组件时清理计时；生成期间禁止重复发送。
- 超时配置从后端估算接口读取，当前本地为 180 秒。浏览器另留 15 秒处理网络与错误返回，随后终止无响应请求。

实现：`vulnscan-frontend/apps/web/src/views/ly/event/detail/components/ChatBox.vue`、`generation-wait.ts`。

## 实际输入内容

请求发送到已配置模型的 `/chat/completions`，包含两个 message：

1. `system`：`EngineerChatSystemPrompt`，定义安全运营助手角色、基于证据、不编造、中文结构化输出。
2. `user`：`ChatService.engineerPromptParts` 按以下顺序拼接业务信息与当前问题。

| 输入部分 | 内容和读取位置 | 裁剪规则 |
|---|---|---|
| 事件基本信息 | `Store.GetEvent`：ID、名称、描述、严重程度、来源、事件状态、轮次、创建时间 | 当前未对单个基本字段另设长度限制 |
| 事件上下文与明细 | `event.Context`：IP、协议、命中次数、首末时间、会话统计、流量统计、IOC、演示标记等 | 明细超过 3 条时取首/中/末样本；单字符串最多 512 字符；上下文最终最多 6000 字符 |
| 报文样本 | 样本的时间、包数、字节数、方向、载荷、TCP 字段等 | 有载荷明文时省略重复 HEX；完整数据仍在数据库和详情接口中 |
| 可观察对象 | `event.Observables` 中的类型、值、角色 | 当前未另设条数上限 |
| 任务 | `Store.ListTasks(eventID)` | 每个 JSON 区块最多 1500 字符，另附截断标记 |
| 动作 | `Store.ListActions(eventID)` | 同上 |
| 命令 | `Store.ListCommands(eventID)` | 同上 |
| 执行结果 | `Store.ListExecutions(eventID)` | 同上 |
| 已有事件总结 | `Store.ListSummaries(eventID)` | 同上 |
| 对话历史 | `Store.ListMessages(eventID)` 中 `engineer_chat` 的用户与 AI 消息 | 最近最多 20 条；单条最多 1000 字符；保留最新、整体约 3000 字符 |
| 当前问题 | 当前输入，清除开头 `@AI` / `@ai` | 当前问题只在末尾出现一次，不重复写进本轮历史 |
| 回答要求 | `deepSOCEngineerAnswerGuide` | 固定研判要求和报告章节模板 |

空的任务、动作等区块写“暂无”，不补造记录。资产台账、SOAR 剧本清单、所有系统角色提示词不会在这条链路中额外查询后整体注入；已有事件或任务里带的相关信息仍可能被包含。

对应代码：`vulnscan-backend/traffic/chat_service.go`、`chat_context.go`、`internal/service/prompts.go`。

## 本地 token 估算快照

问题为“生成报告”，模型为 `k3`，在本轮页面验证发起新对话之前计算：

| 事件 | 输入 token 估算 |
|---|---:|
| demo-event-001 / SSH | 1856 |
| demo-event-002 / WebShell | 1818 |
| demo-event-003 / DNS | 2311 |

DNS 事件逐块估算如下，包含已有的一轮成功报告历史：

| 部分 | 估算 token |
|---|---:|
| 系统提示词 | 144 |
| 事件基本信息 | 81 |
| 事件上下文与明细样本 | 726 |
| 可观察对象 | 29 |
| 任务 | 155 |
| 动作 | 143 |
| 命令 | 9 |
| 执行结果 | 7 |
| 已有事件总结 | 113 |
| 最近工程师对话 | 551 |
| 当前问题及标题 | 11 |
| 报告格式与回答要求 | 335 |

各区块独立向上取整；总输入按整体估算再增加约 12 token 的消息封装开销，因此逐块相加与总数有少量差异。对话增加后，下一轮输入量会变化。

估算复用 `EstimatePromptTokens`：CJK/全角等字符（代码中 rune >= 0x3000）按 0.7 token，其余字符按 1/3.5 token，合计乘 1.1 并向上取整。这是字符启发式，不是 `k3` 官方 tokenizer，不能当作精确计费数；精确数量应以上游 `usage` 为准。

`max_tokens=6000` 是**输出上限**，不是输入数量，也不是每次实际输出量。没有从 token 数推算精准耗时，因为推理、排队与服务负载均会影响延迟。

## 只读估算接口

`POST /api/traffic/engineer-chat/estimate`

```json
{"event_id":"demo-event-003","message":"生成报告"}
```

返回各部分字符数与估算 token、合计输入 token、输出上限、模型和超时配置。仅在本地构造 prompt，不向模型发请求，也不写消息。实际发送复用同一个拼接函数；若两次请求之间新增历史消息，估算可能相应变化。

这份清单针对 `/engineer-chat/send`。按钮“手动刷新分析”走独立的后台自动分析链路 `autoAnalysisPrompt`，其提示词、内容提取与预算不同，不能直接套用此处 token 数。
