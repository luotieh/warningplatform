# 证据输入覆盖与故障定位

本次目标是扩大真实输入覆盖，并让无法判断的原因可查。规则已实现、输入适配器可接入、生产数据实际已具备，是三个不同状态。

## 现在自动获取的输入

| 输入 | 获取方式 | 仍需满足的条件 |
| --- | --- | --- |
| 时间、包数、资产/端点/设备 | 固定快照全量命中、服务端资产登记 | 未知截断不补false；包数未知不补0 |
| HTTP地址、方法、UA | 已保存元数据＋真实HTTP请求解析 | 元数据冲突拒绝；路径不能按端口猜协议 |
| HTTP长度、凭据字段名、编码特征 | 完整payload_hex中的实际请求正文 | 校验报文完整性；只保存脱敏字段名和编码统计，不保存密码值 |
| HTTP响应、表单action | 同记录请求响应＋会话/事务标识＋TCP序号确认 | 序号不吻合拒绝；多表单不选取其中一个冒充全貌；Location不自动变成跳转链 |
| DNS问题、响应码、回答 | 已保存DNS元数据＋完整DNS二进制报文 | 支持UDP及有完整长度前缀的TCP；query不等于成功response |
| 原始载荷、TCP RST | 实际Ethernet帧解析并核验IP、端口、协议 | 不重组IP分片或TCP流；RST不代替完整连接状态机 |
| 资产跨端点观察 | 在内存中复用已绑定命中 | 7项资产规则使用asset://范围；周期性保持每个实际端点独立 |
| TLS SNI | 保存的实际SNI字段 | SNI不等于证书、可信链或指纹证明 |

59项事实均保留输入需求和执行结果。完整名单直接来自`evidence.SupportedFacts/FactInputs`，避免文档另建一份规则枚举。23项语义槽位需求直接来自`SemanticInputContracts`；语义真实材料构建和模型调用尚未接入报告流程，不能把需求清单当作已执行结果。

## 外部补充输入

后端提供`StoreSnapshotSupplemental(ctx, snapshot, inputs)`。可信来源适配/核验任务可以把结果存入现有`traffic_aggregation_records`：

- `kind = evidence_inputs`
- `record_key = <event_id>:<snapshot_version>`
- `group_key = <event_id>`
- 内容类型：`SnapshotSupplementalInputs`，字段见`evidence_supplemental_input.go`。

报告每次只加载该记录一次，随后在内存中共享。读取有10秒超时，最大2 MiB；没有逐算法查库。该入口没有公开HTTP写接口，不读取探针/事件Context中的同名对象。

支持补充规则专属基线、DNS词形语料、审核品牌清单、实际服务目录、ASN/国家/信誉、核验会话、TLS证书及信任/例外/指纹库、历史独立研判、阶段和战役证明、授权任务、独立规则与情报元数据以及核验群体。Policies可提供定义中要求的明确策略参数，非法策略拒绝；不默认编造阈值或正常业务基线。

校验要求：

1. event_id、snapshot_version精确匹配，不接受跨版本补充。
2. 每个Input的Scope和半开窗口必须精确匹配已构建输入；asset://范围也可以补充。
3. 来源必须具备Verified、Complete、Version和非空SourceIDs。写入口是可信后端桥接，不能让探针或模型自证这些字段。
4. 补充记录不能替换原始DNS/HTTP/连接观察，避免用样本覆盖全量分母。
5. 会话成员、TLS记录、群体成员命中必须绑定当前快照的真实命中、对象及时间；群体成员必须核验，不能从IOC标签推断感染群体。
6. 算法仍检查基线指标合法性、历史窗口、定谳来源、战役归属、授权时间/端口/协议等；补充入口不是绕过规则的通道。

**尚未自动覆盖：** 当前没有完整的正常流量基线生成任务、独立历史定谳/战役登记、品牌授权、TLS信任指纹维护、群体归属核验等生产来源任务。本次实现了接入及诊断机制，没有伪造这些来源。HTTP分段流、加密明文、完整跳转事务链、不支持的正文结构和完整连接状态也不会靠模型补齐。人工通报审核approved/rejected不等于恶意/误报定谳；session_summary线缆字节不等于载荷字节。

## 查问题的入口

在现有流量模块路由前缀下调用：

```text
GET /events/detail/<event_id>/evidence-diagnostics?snapshot_version=<version>
```

省略版本或传0读取最新快照。沿用现有流量事件授权路由机制。接口只读诊断，不重新运行算法、不读全量命中。

返回包括event_id、snapshot_version、执行时间、status/reason、result_key、result_persisted及manifest。重点看：

- `fact_coverage`：全部59项的范围、是否请求、结果、reason_code和输入类型；多范围可以有多条同规则记录。
- `issues`：阶段、错误码、字段路径、hit_id、分析对象、是否可重试；存储故障还保留安全的cause_type、MySQL数字错误码或取消/超时类别，不保存驱动错误原文。
- `declared_hits/loaded_hits/bound_hits/unresolved_hits`：区分取数不全与资产归属失败。
- `read_pages/revision_batches`：核对读取是否异常增加。
- `missing_inputs`：某些范围尚缺的数据来源类别；不是精确字段就绪承诺，逐规则原因优先。
- `issue_count/omitted_issues`：详细问题最多128条，超出明确记录总数，不静默丢失。

完整规则结果保存在`evidence_result`；最后一次诊断保存在`evidence_diagnostics`；核心输入异常最后一次故障保存在`evidence_failure`，按事件＋快照查询。日志以`[evidence]`开头，含事件/版本/错误码；底层错误可通过Go错误链定位，不把SQL、密码或驱动原文送给报告模型。

建议排查顺序：先核对版本，再看计数和coverage，再查具体规则reason_code，最后按issues的hit_id读取原始记录。`not_requested`、`unavailable`、`missing`均不能解释成行为不存在。

## 故障行为

| 问题 | 行为 |
| --- | --- |
| 单字段缺失、协议解析失败 | 保留已有可信字段，记录命中和字段；相关规则missing |
| 补充记录不存在/非法/来源未核验 | 明确原因，其他真实事实继续执行 |
| 补充查询暂时失败 | 可重试，当前结果不缓存，下次重新读取 |
| 核心命中读取失败、重复身份、成员数不符 | 不发布算法结论，记录故障，报告原有统计仍可使用 |
| 缓存损坏或版本不符 | 记录日志并重算 |
| 缓存或诊断写失败 | 日志明确失败，保留当前计算，标记未持久化，不宣称已保存 |
| 执行取消 | 正常向上传递，不转成正常的缺失结果 |
| 数据/范围/报文预算超过 | 明确budget错误，不使用半份材料冒充完整输入 |

当前默认集中读取上限：20000条、16 MiB、256个端点范围；单报文1 MiB，补充记录2 MiB。可由后端调用者调整。覆盖范围仅限快照已保存命中，不代表所有网络通信。

## 验证边界

新增测试使用正常摄入和Store读写链路，覆盖完整/截断HTTP、脱敏、DNS查询与应答、真实响应配对、跨端点资产规则、补充数据绑定与来源拒绝、内容变更失效缓存、读取故障、重试与诊断限额。它们验证实现契约；真实生产库/探针和实际补充来源仍需要部署环境验收。
